# Scoped knowledge-base initialization

**Agent:** Knowledge

## Fixture

Use a disposable workspace containing at least four immediate child repositories
under `repositories/`: `service-a`, `service-b`, `service-c` and `service-d`.

Ensure `service-a` contains source or configuration evidence of a dependency or
runtime integration with `service-c`, while `service-d` is unrelated.

Start with an empty `knowledge-base/`.

## Prompt 1 — scoped initialization

```text
/knowledge-init service-a service-b
```

## Expected behavior

- Invokes `repository_inventory` and retains the complete workspace repository
  inventory for validation and coverage.
- Performs detailed repository inspection only for `service-a` and `service-b`.
- May represent the supported relationship from `service-a` to `service-c`.
- Does not deeply inspect `service-c` merely because it is referenced.
- Does not deeply inspect unrelated `service-d`.
- Creates or updates the single knowledge base under `knowledge-base/`.
- Records coverage so `service-a` and `service-b` are distinguishable from
  repositories that are referenced or not analysed.
- Does not mark `service-c` as analysed solely because it is referenced.
- Reports incomplete workspace coverage.

## Prompt 2 — incremental second slice

Run in a new session without deleting the knowledge generated by Prompt 1:

```text
/knowledge-init service-c service-d
```

## Expected behavior

- Preserves valid knowledge created for `service-a` and `service-b`.
- Performs detailed analysis for `service-c` and `service-d`.
- Merges new cross-repository findings into the existing workspace knowledge.
- Progressively strengthens repository coverage without duplicating repository
  representations or relationships.
- Invokes `knowledge_coverage` to merge the second slice into cumulative
  repository coverage; the agent does not `edit`, patch or manually rewrite
  coverage rows.
- Persists repository coverage under the exact heading
  `## Repository coverage` (not Setext syntax or another heading level).
- Leaves exactly one coverage representation for each canonical repository;
  `service-c` and `service-d` must replace their stale `not analysed` entries
  when they become analysed.
- The tool-owned `## Repository coverage` section contains no stale rows from
  the previous run and exactly one entry per canonical logical repository.
- Reads back the updated workspace overview and verifies it against the
  `knowledge_coverage` result; it does not attempt manual repair if the tool
  reports a validation failure.
- Preserves unchanged coverage for repositories outside the second slice.
- Does not accumulate `Scope of this run` lines in the persistent workspace
  overview; current scope belongs in the command report, not workspace state.
- Removes or rewrites first-run-only prose that is no longer true after the
  second slice (for example, claims that no prior knowledge base existed).
- Does not downgrade previously analysed repositories.

## Prompt 3 — backward compatibility

Run with a fresh copy of the fixture:

```text
/knowledge-init
```

## Expected behavior

- Retains the existing full-workspace initialization behavior.
- Treats every canonical workspace repository as part of the detailed analysis
  scope.

## Failure checks

Also verify that a scoped invocation with an unknown repository identifier does
not silently select a similarly named or nested repository and clearly reports
the invalid scope.
